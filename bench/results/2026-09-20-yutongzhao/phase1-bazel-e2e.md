## 7. server-side view
```
$ grep -c '"status":404' node log   # cache misses during the populating build
0
$ grep -c '"status":201' node log   # objects newly stored
2700
$ grep -c '"status":200' node log   # hits served
1202
$ grep -c '"level":"ERROR"' node log
0
```

The 404 count is zero because a cache miss is logged at `debug` level and this node ran at
the default `info` level. That is deliberate — a cold build produces one miss per action and
logging each at `info` would bury everything else — but it means this particular line is not
evidence of anything. The misses are visible instead in step 3: Bazel reports `600
linux-sandbox` processes, meaning every action was executed locally rather than served.

## What this run does and does not establish

Established:

- Bazel speaks to KilnCache with no adapter: `--remote_cache=http://127.0.0.1:18080` and
  nothing else.
- A populating build stores 2,100 CAS objects and 600 action-cache entries.
- After `bazel clean --expunge`, a rebuild is served entirely from the cache: 600 of 600
  executable actions are remote cache hits and zero compiler processes run.
- All 320 build outputs are byte-for-byte identical to the locally-compiled ones. The
  combined digest `860cf190…` is the same in step 2 and step 6.
- No partial uploads were left behind, and the node logged no errors.

Not established by this run:

- Any timing claim. One sample each, on a machine that was also running the test suite.
  Phase 5 repeats every case at least five times and publishes the distribution.
- Anything about three nodes, replication, eviction or failure. Those are Phases 2 and 3.
