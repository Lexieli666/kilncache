# bazel-cpp benchmark fixture

Generated by `scripts/gen-bazel-fixture.sh`. **Do not edit by hand** —
regenerating overwrites `src/`.

- 280 `cc_library` targets across 8 layers
- 20 `cc_binary` targets
- 300 targets total
- Seed `20260920`, so the sources are byte-identical on every
  generation and a build measured today is comparable to one measured
  next month.

## Build it

```bash
cd fixtures/bazel-cpp
bazel build //...                                        # local only
bazel build //... --config=remote \
      --remote_cache=http://localhost:8080               # through KilnCache
```

## Measure a cache-served rebuild

```bash
bazel build //... --config=remote --remote_cache=http://localhost:8080
bazel clean --expunge
bazel build //... --config=remote --remote_cache=http://localhost:8080
```

The second build should report remote cache hits for nearly every
action. `scripts/bazel-bench.sh` automates this and records the raw
numbers; nothing here is meant to be timed by hand.

The C++ is deliberately dull. It exists to give the compiler a known,
repeatable quantity of work with a realistic dependency depth.

## Why the generated sources are committed

They are machine-generated and deterministic, so in principle the generator
alone would be enough. They are committed anyway for two reasons:

1. **The benchmark has to stay comparable.** A number measured today is only
   meaningful next to one measured next month if the workload is literally the
   same bytes. Committing the sources makes that a fact rather than a property
   of the generator that a future edit could quietly break.
2. **A clean checkout must build without extra tooling.** The generator needs
   Python; the benchmark should not.

The consequence is that regenerating with different parameters produces a large
diff. That is the correct signal: the workload changed, and any benchmark
comparison across that commit is invalid.
